# 改修プラン (2026-08-28)

対象は `hepta-chord/pocket-rogue` の `main` (e630b87) である。
テストは 191 件すべて通る状態から始める。

## 1. 現状の計測

`npm run balance -- 200` と、到達レベルを見る補助スクリプトの結果である。

| 指標 | 実測 |
|---|---|
| 最終レベル 中央値 | 24 |
| B10 到達時のレベル 中央値 | 26 |
| B20 到達時のレベル 中央値 | 35 (最小 31、最大 52) |
| 1 階の滞在ターン (B10 以降) | 140〜153 |
| 総ターン 中央値 | 1772 |
| 総撃破 中央値 | 155 |
| 被弾の軽減率 | 57〜62% |
| 1 ダメージに潰れる率 (B4〜B9) | 70〜83% |
| 死因 1 位 | スタミナ切れ 56/200 (28%) |

B20 でレベル 35 は最大 HP 122 である。
同じ階の被弾は実ダメージ平均 1.97 なので、無抵抗で 62 発耐える計算になる。
「ぜんぜん死ぬ気がしない」という体感は、この比が正しく反映されたものである。

死因の 1 位が敵ではなくスタミナ切れなのは、1 階が長いことの帰結である。
スタミナは 7 ターンに 1 減るので初期値 150 は約 1050 ターンぶんであり、
B10 到達までの累計滞在ターンとほぼ一致する。
つまり今のゲームは、敵と戦って死ぬのではなく時間切れで死ぬ形になっている。

## 2. 診断

### 2.1 角越しの攻撃 (最優先)

移動は角の斜め抜けを禁じているのに、攻撃は距離だけで判定している。

- プレイヤー: `src/game.ts:329` で `monsterAt(nx, ny)` を先に見て、
  `canStep` を通さずに `playerAttack` を呼ぶ
- 敵: `src/game.ts:1220` の `dist === 1` で即攻撃する。`dist` はチェビシェフ距離である
- 群れ薙ぎ: `adjacentMonsters` (`src/game.ts:1033`) も同じくチェビシェフ距離だけで拾う

両者とも壁の角越しに殴れるので、通路の入口が防衛線にならない。
通路に 2 歩入らないと 1:1 にならないのは、この非対称ではなく「両者とも角を抜ける」ことが原因である。

### 2.2 敵の思考ルーチンが列を作る

`moveToward` (`src/game.ts:1299`) は候補を 3 つしか試さない。

```ts
const candidates = [[sx, sy], [sx, 0], [0, sy]];
```

3 つとも壁か他の敵で塞がると、その場に留まる。
迂回する候補が無いので、先頭の 1 体が詰まると後続は直線に並んで停止する。
群れ (`pack` が 2〜5) が数の利を出せないのはこのためである。

包囲が成立しないのも同じ理由で、全員が同じ最短方向へ向かうので 1 列になる。

### 2.3 レベルが上がりすぎる

獲得側と必要側の伸び方が釣り合っていない。

- 獲得: 1 階の敵数が `3 + depth + 0..2` で線形に増え、
  基礎経験値がグレードで 4 → 13 → 30 と跳ね、さらに `1 + 0.15 × depth` が掛かる。
  累計はおよそ深さの 3 乗で伸びる
- 必要: `xpToNext(level) = 6 + level(level+1)/2` は 2 次なので、累計は 3 乗で伸びる

3 乗どうしなので、レベルは階に対してほぼ線形になる。実測で 1.7 レベル/階である。
README の「どの階でも 3〜10 体で 1 レベル」という狙いは達成されているが、
1 階で 15〜24 体倒すので、狙いどおりに動いた結果としてレベルが 35 まで伸びる。

さらにレベルアップが全回復なので、経験値が実質「無限の回復薬」として働く。
下降圧 (スタミナ、毒、追う者) を足しても、レベルアップの頻度がそれを上回っている。

### 2.4 分裂体が野放しになっている (バグ)

`trySplit` (`src/game.ts:1155`) の上限判定が、グレード 1 の `slime` だけを数えている。

```ts
const slimes = state.monsters.filter((x) => x.kind === 'slime').length;
if (slimes >= SLIME_CAP) return;
```

`slime` の `maxDepth` は 10 なので、B11 以降に出る `slimeSplit` と `slimeMimic` では
この数が常に 0 になり、上限 4 が一度も働かない。

分裂した子は HP が半分になるだけで、`rewardKill` は `def.xp` から経験値を出す。
つまり殴って割るたびに経験値の総量が増える。
B11 以降で無限に経験値を稼げる状態であり、2.3 のレベル過剰を後押ししている。

README の「4 匹まで」という記述とも食い違っている。

あわせて、分裂体は `spawned` が立たないのでドロップ抽選も満額の 16% を引く。
装備も経験値も、割るたびに湧き口が増える状態である。

### 2.5 防具が効きすぎる

軽減率は 60% 前後で上限の 75% には届いていないが、
出目そのものが小さいので、B4〜B9 では被弾の 7〜8 割が 1 ダメージに潰れている。
被弾しても減らないので、階に留まる判断が軽くなり、滞在ターンを押し上げている。

### 2.6 1 階が長い

40 × 30 の格子に部屋を最大 9 つ置き、視界は 7 マスである。
階段を探し、アイテムを拾い、湧いた敵を掃除すると 140 ターン前後かかる。

## 3. 改修の順番

数値の調整を先にやると、戦闘の形が変わったあとに測り直しになる。
戦い方を決める改修 (到達判定と AI) を先に置き、計測する側 (autoplay) を合わせてから数値を触る。

```

Step 2  敵の思考ルーチンを作り直す (src/ai.ts に切り出す)
Step 3  autoplay に通路戦術を入れる
Step 4  1 階を短くする
Step 5  経験値ゲートを入れ、成長曲線と防御を合わせる
Step 6  game.ts を分割する
Step 7  新要素を足す
```

Step 0 から 3 までは数値を触らない。
Step 4 と 5 で初めてバランスを動かし、そこで一度まとめて計測する。

## Step 0: 分裂まわり

3 つある。いずれも数値のバランスに触るので、まとめて 1 つのコミットにする。

### 0.1 上限が効いていない (バグ)

`trySplit` (`src/game.ts:1155`) の上限判定が、グレード 1 の `slime` だけを数えている。
`slime` の `maxDepth` は 10 なので、B11 以降の `slimeSplit` と `slimeMimic` では
この数が常に 0 になり、上限 4 が一度も働かない。

```ts
const kin = state.monsters.filter((x) => x.kind === m.kind).length;
if (kin >= SLIME_CAP) return;
```

### 0.2 分裂体が親と同じ報酬を得ている

`dropEquip` (`src/game.ts:1066`) と `rewardKill` (`src/game.ts:1081`) は
`m.spawned` しか見ていない。`trySplit` で作られる子は `spawned` を立てないので、
ドロップ・経験値・スコアがすべて満額になる。

`Actor` に `split?: boolean` を足し、`trySplit` で立てる。扱いは次のとおり。

| 報酬 | 分裂体 |
|---|---|
| ドロップ | なし (抽選しない) |
| 経験値 | `SPLIT_REWARD` を掛ける |
| スコア | `SPLIT_REWARD` を掛ける |

ドロップを 0 にしても、odd 系統の装備 (祓いの杖・変則よけの護符) は
どちらも `dropOnly: false` で床にも出るので、入手経路は残る。
分裂を止める武器が分裂で稼げる、という循環が切れる。

`spawned` を流用しないのは、ドロップを半減ではなく 0 にしたいからである。

### 0.3 SPLIT_REWARD を決める

分裂は親が HP を半分渡す形なので、倒すのに必要な総ダメージは変わらない。
労力が同じまま報酬だけが増えるので、係数が大きいと稼ぎ場になる。

上限 4 のとき子は 3 体なので、合計は `1 + 3 × SPLIT_REWARD` 倍になる。

`spawnMonsters` は 1 回の抽選で pack をまとめて置くので、
系統の比較は「抽選 1 回あたりの基礎経験値」で行う。
深さ倍率は全系統に等しく掛かるため、基礎値だけで比べられる。

| グレード | 群れ | 俊敏 | 戦士 | 重装 | 変則 (分裂なし) | 係数 0.5 | 係数 0.2 |
|---|---|---|---|---|---|---|---|
| 1 | 5.0 | 3.0 | 4.0 | 16.0 | 3.0 | 7.5 | 4.8 |
| 2 | 24.0 | 15.0 | 14.0 | 34.0 | 8.0 | 20.0 | 12.8 |
| 3 | 96.0 | 45.0 | 40.0 | 70.0 | 22.0 | 55.0 | 35.2 |

係数 0.5 (合計 2.5 倍) だと、グレード 1 で変則が重装に次ぐ 2 番手になる。
係数 0.2 (合計 1.6 倍) なら、3 グレードとも戦士と俊敏のすぐ下に収まる。

**`SPLIT_REWARD = 0.2` を初期値とする。**

変則は「通常の戦い方が通じない」系統であって稼ぎ場ではないので、
戦士・俊敏よりわずかに下に置くのが位置づけに合う。

`def.xp` を下げる案 (2.5 で割る) は採らない。
祓いの杖で分裂を止めたときの報酬が極端に低くなり、
分裂を止める手段を使うと損をする形になるためである。

### 0.4 検証には計測の追加が要る

現在の `npm run balance` は系統別の内訳を出さない。
`DepthStats` が持つのは撃破数とレベルアップ回数だけで、系統も経験値も記録していない。
このままでは「他系統と揃ったか」を確認できない。

`src/sim/autoplay.ts` と `src/sim/report.ts` に次を足す。

- `RunResult` に系統ごとの撃破数と獲得経験値を持たせる
  (`killMonster` を通るので、`setDamageObserver` と同じ形の観測フックを 1 つ足せば取れる)
- レポートに「系統ごとの経験値の寄与 (%)」の表を出す

0.2 は机上の初期値である。この計測を入れてから合わせ直す。

### 受け入れ条件

- B11 以降で同種スライムが 5 体以上同時に存在しない
- 分裂体を倒しても装備が落ちない
- 分裂体の経験値とスコアが親の 0.2 倍になる
- 系統ごとの経験値寄与の表が出ること
- その表で、変則の寄与が戦士・俊敏を上回らないこと

### 補足: グレード間で経験値と HP の比がずれている

0.3 の表を作る過程で見つけた別件である。

| グレード | 経験値 / HP の目安 |
|---|---|
| 1 | 0.4〜0.6 |
| 3 | 1.1〜1.9 |

深さ倍率 (`1 + 0.15 × depth`) と二重に効いて、深層の経験値収入を押し上げている。
2.3 のレベル過剰のもう 1 つの原因なので、Step 5 で成長曲線を触るときに一緒に見る。

## Step 1: 攻撃の到達判定

### やること

`src/map.ts` に到達判定を足す。実体は `canStep` と同じ規則だが、意味が違うので名前を分ける。

```ts
/** (x, y) から (dx, dy) の隣へ攻撃が届くか。壁の角越しには届かない */
export function canReach(map: GameMap, x: number, y: number, dx: number, dy: number): boolean {
  return canStep(map, x, y, dx, dy);
}
```

呼び出し側を 3 か所直す。

1. `src/game.ts:329` プレイヤーの攻撃
   `monsterAt` が居ても `canReach` が false なら攻撃させず、ターンも消費しない
2. `src/game.ts:1220` 敵の攻撃
   `dist === 1` を「距離 1 かつ `canReach` が true」に変える
3. `src/game.ts:1033` `adjacentMonsters` (群れ薙ぎ)
   同じ制限をかける

棘鎧の反撃 (`thornsCounter`) は `monsterAttack` の中から呼ばれるので、
2 を直せば自動的に追随する。

### 角越しを能力として切り出す

`Passive` に `reach` を足し、これを持つ敵だけが角越しと距離 2 の攻撃を行えるようにする。

- `phasing` (壁抜け) は既に角の制限を受けない設計なので、そのまま例外として残す
- ドラゴンの `breath` は距離 2〜4 の技として既に分かれているので、変更しない
- 現時点で `reach` を持つ敵は作らない。Step 7 で槍型の敵を足すときに使う

こうすると「角越しに殴られたら、それは遠距離攻撃を持つ敵である」と読めるようになる。

### 影響と確認

通路の入口に立てば、部屋側の敵は正面の 1 体しか殴れなくなる。
1 歩で防衛線が成立するので、2 歩入り込む必要が消える。

連結性は変わらない。
`canStep` は `map.test.ts` の到達判定と同じ規則で、部屋は矩形・通路は直交線なので
「角越しでしか届かない位置に敵が固定される」状況は生まれない。
ただし念のため、次のテストを足す。

- 壁の角を挟んで斜めに並んだプレイヤーと敵が、互いに攻撃できないこと
- 同じ配置で `phasing` を持つ敵は攻撃できること
- 群れ薙ぎが角越しの敵を巻き込まないこと

受け入れ条件

- 既存の 191 件が通ること
- 上記 3 件のテストが通ること
- `npm run balance -- 200` で被弾回数が減ること (通路で戦えるようになるため)

## Step 2: 敵の思考ルーチン

### 狙い

3 つを同時に満たす。

| 場面 | 望ましい挙動 |
|---|---|
| 通路 | 1 体が接敵し、残りは後ろで列を作る (現状も正しい) |
| 部屋 | 散って囲む (現状できていない) |
| 塞がれたとき | 迂回する (現状は停止する) |

現状の `moveToward` は候補が `[sx, sy] [sx, 0] [0, sy]` の 3 つしかない。
3 つとも塞がると停止するので、部屋でも通路と同じ列ができる。

### 距離場

`src/ai.ts` を新設し、プレイヤーからの歩数を持つ距離場を作る。

```ts
/** プレイヤーからの歩数。canStep の規則。届かないマスは -1 */
export function distanceField(map: GameMap, from: { x: number; y: number }): Int32Array;
```

- 8 方向の幅優先探索で、`canStep` の角の制限をそのまま使う
- **敵は障害物として扱わない**。扱うと敵が動くたびに作り直しになる
- 40 × 30 = 1200 マスなので、1 ターン 1 枚なら負荷にならない

作る場所は `monstersAct` の先頭である。
`endTurn` は鈍足の効果で `monstersAct` を 2 回呼ぶことがあるので、
ターンごとではなく `monstersAct` ごとに作る。
その間プレイヤーは動かないので、1 回の `monstersAct` の中では使い回してよい。

### 1 歩の決め方

```
here  = field[m の位置]
cands = 通れて空いている隣接マス (canStep の規則)

down  = cands のうち field < here     // 寄る
if down が空でない:
    field 最小 → プレイヤー方向との内積が大 → rng の順で 1 つ選ぶ
    return それ

if 隘路(m):                            // 通路では列を作るのが正しい
    return null                        // 待機

side  = cands のうち field == here     // 横にずれる
if side が空でない:
    「隣に field == 1 のマスがある」ものを優先して 1 つ選ぶ
    return それ

return null                            // 待機
```

`隘路(m)` は「m の周囲で歩けるマスが 2 以下」で判定する。

### なぜこれで囲めるか

`down` が空になるのは、寄れるマスがすべて他の敵に塞がれているときである。
つまり先頭が席を取り、後続が押している状態を指す。

そこで `side` (同じ距離への横移動) を許すと、後続は横へ回り込む。
部屋なら同じ距離のマスが周囲に多いので自然に散り、
通路なら横が壁なので `side` が空になり、列のまま止まる。

席の予約表を持たなくても、地形の違いだけで挙動が分かれる。
これが最小の実装で狙いを満たす形である。

`隘路(m)` の判定を挟むのは、通路の中で無駄な横移動が起きないようにするためである。

### 足りなかった場合の次の手

上の形で「部屋で 3 体中 2 体以上が隣接する」を満たせないときに限り、席の予約を足す。
先に作らない。20 行で済むものを 80 行にする前に、計測で必要性を確かめる。

席の予約は次の形になる。

1. `monstersAct` のループに入る前に、視界内の `swarm` をプレイヤーに近い順に並べる
2. 席の候補を集める。プレイヤーの周囲 8 マスのうち、歩けて、
   `canReach` でプレイヤーに届き (角越しは席にならない)、空いているマス
3. 各敵に、未予約の席のうち自分に最も近いものを割り当てる
4. 割り当てた席への距離場を下る

席は最大 8 個なので距離場も最大 8 枚である。
1200 × 8 = 9600 マスで、ターン制なので体感には出ない。

### 既存のパッシブとの噛み合わせ

| パッシブ | 扱い |
|---|---|
| `phasing` (壁抜け) | 距離場を使わず、現状の greedy のままにする。壁を抜けるので詰まらず、専用の距離場を作る意味が薄い |
| `erratic` (ふらつき) | 確率で `down` の最良ではないものを選ぶ。今の「完全にランダムな方向」から置き換える |
| `mimic` (擬態) | 動かないので対象外 |
| `fast` / `slow` | 手番の制御なので変更しない |
| `regen` | 移動と無関係 |

見えていないときの徘徊は現状のままとする。
`sees` の判定 (`state.visible` を敵の位置で引く) も変えない。

### 受け入れ条件

テストは `src/ai.test.ts` に置く。

- 幅 1 の通路の先にプレイヤー、通路に群れ 3 体を置く
  → 10 ターン以内に 1 体が隣接し、残り 2 体は隣接しない (列)
- 開けた部屋にプレイヤー、周囲に群れ 3 体を置く
  → 10 ターン以内に 2 体以上がプレイヤーに隣接する (包囲)
- 敵の正面を別の敵で塞ぐ
  → 停止せず、横か迂回で寄る
- `phasing` を持つ敵が壁の中を通ってプレイヤーへ寄る (現状維持の確認)
- `npm run balance -- 200` で B1〜B10 の被弾回数が現状より増える

最後の 1 つが満たせなければ AI が働いていない。
数値ではなく実装を疑う。

## Step 3: autoplay に通路戦術

計測する側が新しい戦い方を使えないと、
「AI が損な戦い方をしている」前提で数値を過剰に緩めてしまう。
Step 5 の前に必ず入れる。

`src/sim/autoplay.ts` の `decide` に、隣接判定の前段として次を足す。

```ts
/** 歩ける隣接マスが 2 以下なら隘路とみなす */
function isChoke(state: GameState, x: number, y: number): boolean;
```

方針

1. 見えている敵が 2 体以上で、自分が隘路に居ないとき、
   最も近い隘路へ BFS で後退する (敵から遠ざかる向きを優先する)
2. 隘路に着いたら、敵が隣接するまで `wait` する
3. 隣接したら殴る (今の挙動)
4. 敵が 1 体だけなら、これまでどおり突っ込む
5. 後退の途中で HP が `potionAt` を割ったら、これまでどおり回復を優先する

`Policy` に次を足して、切り替えられるようにする。

```ts
/** この数以上の敵が見えたら隘路へ下がる。0 で無効 */
chokeAt: number;   // 既定 2
/** 隘路を探す範囲 (歩数) */
chokeRange: number; // 既定 8
```

`chokeAt: 0` にすれば従来の方針で回せるので、
「戦術の有無で到達階がどう変わるか」を比較できる。

受け入れ条件

- `chokeAt: 0` と `chokeAt: 2` の両方で 200 run が完走すること
- `chokeAt: 2` の方が B10 到達率が高いこと
  (高くならなければ、Step 1 と 2 のどちらかが意図どおりに効いていない)

## Step 4: 1 階を短くする

滞在 140〜150 ターンを 60〜80 に落とす。
手は 4 つあるが、推奨は上 2 つの併用である。

### 推奨する 2 つ

1. マップを縮める
   `MAP_W` 40 → 32、`MAP_H` 30 → 24、`MAX_ROOMS` 9 → 6。
   歩数がそのまま減る。視界 7 は据え置く (縮めると相対的に広くなる)

2. 敵の予算を減らして 1 体を濃くする
   `spawnMonsters` の `budget` を `3 + depth + 0..2` から `3 + depth/2 + 0..1` に。
   減らしたぶん、基礎 HP と攻撃力を上げて 1 体あたりの重みを戻す。

   この項目の目的は**ターンの短縮だけ**である。
   当初は経験値の抑制も兼ねていたが、Step 5.1 の経験値ゲートがそちらを引き受けるので、
   「経験値を減らすために頭数を削る」という動機は消えている。
   削る量は、掃討にかかるターンだけを見て決めればよい

### 採らない 2 つ

3. 階段の方角を降りた直後に出す
   `stairsDirection` (`src/game.ts:1423`) が既にあるので実装は簡単だが、
   探索そのものを削るので、暗闇階に限る形でのみ検討する

4. アイテムを階段寄りに配置する
   寄り道が減るのは確かだが、「危ない方へ取りに行くか」という判断まで消える

### 受け入れ条件

- B10 以降の滞在ターンが 60〜80 に入ること
- 総ターン中央値が 900〜1100 に入ること
- 死因のスタミナ切れが 10% 以下に下がること
- マップ縮小後も `map.test.ts` の連結性テストが通ること
  (部屋が 6 つに減るので、生成の失敗率が上がっていないかも見る)

## Step 5: 経験値ゲートと成長曲線

ここで初めて数値を触る。
Step 0 から 4 までで撃破数と被弾が動くので、先に計測し直してから決める。

### 5.1 経験値ゲート (主軸)

レベルを階数に紐づけ、進みすぎたぶんの取得経験値を減衰させる。

```ts
/** 基準線の余裕。level が depth + GATE_SLACK を超えると減衰が始まる */
export const GATE_SLACK = 3;

function gateRate(level: number, depth: number): number {
  const over = level - (depth + GATE_SLACK);
  return over <= 0 ? 1 : 1 / (1 + over);
}
```

`GATE_SLACK = 3` なら基準線は B1 で Lv 4、B10 で Lv 13、B20 で Lv 23 になる。

**減衰だけをかけ、増幅はしない。**
下回ったときに増やす形にすると、階段直行で潜って深い階で一気に回収する抜け道ができる。
README の「階層を降りただけでは強くならないので、倒す敵を選ぶことが判断になる」と衝突する。

減衰だけなら、潜ることの効果は「基準線が上がって減衰が外れる」だけになる。
潜る動機にはなるが、潜っただけでは強くならない。

#### ゲートで不要になるもの

| 項目 | ゲート導入後 |
|---|---|
| 必要経験値を三次にする | 不要。現行の二次のままでよい |
| `SPLIT_REWARD` の精密な合わせ込み | 大まかでよい。稼いでも基準線で止まる |
| `SPAWN_REWARD` (湧きの報酬半減) | 残してよいが重要度が下がる |

稼ぎ手段を個別に潰す必要がなくなり、調整点が `GATE_SLACK` の 1 つに集約される。
これがこの案の最大の利点である。

#### 併せて要るもの

1. 減衰を見せる

同じ敵を倒したのに経験値が違う理由が分からないと理不尽になる。
`gainXp` のログに出す。

```
ネズミを倒した。経験値 3 (深さに対してレベルが高いため 12 → 3)
```

2. 減衰したぶんをスコアに変換する

基準線に張り付くと経験値がほぼ無意味になり、倒す動機が消える。
失ったぶんをスコアへ流す。

```ts
const full = xpFor(def, state.depth);
const got = Math.ceil(full * gateRate(state.level, state.depth));
state.score += full - got;
gainXp(state, got);
```

ハイスコアという別軸に残るので、「レベルが頭打ちになったぶんは点が伸びる」と読める。

#### レベルアップの全回復について

ゲートでレベルアップの頻度が下がるぶん、回復機会も減る。
そのため当初案の「全回復をやめて 1/2 回復にする」は不要になる可能性が高い。

全回復は README にある「瀕死のまま踏み込んで全回復を取りにいくかどうかが判断になる」という
設計の核なので、残せるなら残す。ゲートを入れたあとに計測して決める。

### 5.2 レベルあたりの最大 HP

ゲートで到達レベルが 35 から 23 前後に下がるので、`LEVEL_HP = 3` のままだと
最大 HP は 20 + 22 × 3 = 86 になる。

B20 の出目平均 4.84 に対して 18 発ぶんである。
現状の 62 発よりは締まるが、まだ緩い。`LEVEL_HP` を 2 にすると 64 で 13 発になる。

ゲートと `LEVEL_HP` のどちらで詰めるかは計測してから決める。
先に `GATE_SLACK` だけを入れて測り、足りない分を `LEVEL_HP` で詰めるのが切り分けやすい。

### 5.3 グレード間の経験値と HP の比

Step 0 の補足で記録したずれをここで直す。

| グレード | 経験値 / HP の目安 |
|---|---|
| 1 | 0.4〜0.6 |
| 3 | 1.1〜1.9 |

深さ倍率 (`1 + 0.15 × depth`) と二重に効いて、深層の経験値収入を押し上げている。

ゲートを入れると収入の絶対値は抑えられるが、系統ごとの相対的な釣り合いは直らない。
グレード 3 の `def.xp` を下げるか、`XP_DEPTH_RATE` を下げるかを、
Step 0.4 で足した系統別の内訳を見て決める。

### 5.4 防御

1 ダメージに潰れる率を 40% 以下に落とす。

- 「出目の 1/4 は必ず通る」を 1/3 にする
- または被ダメージの下限を 2 にする (出目が 2 以上のとき)

前者を推す。後者は序盤の弱い攻撃まで重くなる。

### 受け入れ条件

| 指標 | 現状 | 目標 |
|---|---|---|
| B20 到達時のレベル | 35 | 18〜22 |
| 1 ダメージ率 (B4〜B9) | 70〜83% | 40% 以下 |
| B10 到達率 | 83% | 60〜70% |
| B20 到達率 | 11% | 20〜25% |
| 死因のスタミナ切れ | 28% | 10% 以下 |

B20 到達率を上げつつ B10 到達率を下げるのは、
「序盤で気を抜くと死ぬが、上手く進めば深くまで行ける」形にするためである。
今は逆で、序盤は死なないが深層で時間切れになる。

ゲートを入れたあとはレベルが基準線にほぼ張り付くはずである。
`balance` のレポートに「階ごとのレベル中央値」を足し、基準線との差を見られるようにする。
差が開いたままなら、ゲートではなく別の要因が効いている。

## 5. 残っている論点

### 5.1 頭数の削減と包囲の両立

Step 4 の「敵の予算を減らす」は、群れ (`swarm`) の設計とぶつかる。
群れは数で押す系統なので、頭数を削ると Step 2 で直した包囲が発動しにくくなる。

Step 2 の包囲は席の予約ではなく横移動で成立させる形なので、
必要なのは「同時に寄れる敵が 2〜3 体」であって、大量の頭数ではない。
そのため衝突は当初の見込みより小さいが、`pack` を削ると 1 グループで包囲が成立しなくなる。

削減は群れ以外に限る (群れの `pack` は維持し、単体で出る系統の抽選回数を減らす) のが素直である。
Step 4 のときに、群れの `pack` を維持した場合としない場合の両方を測って決める。

### 5.2 ゲートの基準線をどこに置くか

`GATE_SLACK = 3` は、プランの目標 (B20 で Lv 18〜22) から逆算した初期値である。
実際には Step 4 の頭数削減で経験値の総量が減るので、
ゲートに当たる前に基準線を下回る run が出る可能性がある。

その場合はゲートが働かず、レベルの分布が run ごとにばらつく。
`balance` に「階ごとのレベル中央値」を足したうえで、
基準線に張り付いている run の割合を見て `GATE_SLACK` を決める。

張り付く run が半分に満たないなら、ゲートは効いていない。
その状態で `GATE_SLACK` を下げても意味がないので、
Step 4 の削減量を戻すか、`LEVEL_HP` 側で詰める。

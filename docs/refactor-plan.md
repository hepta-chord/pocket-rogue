# 改修プラン (2026-08-28)

対象は `hepta-chord/pocket-rogue` の `main` (e630b87) である。
テストは 191 件すべて通る状態から始める。

## 1. 現状の計測

`npm run balance -- 200` と、到達レベルを見る補助スクリプトの結果である。

| 指標 | 実測 |
|---|---|
| 最終レベル 中央値 | 24 |
| B10 到達時のレベル 中央値 | 26 |
| B20 到達時のレベル 中央値 | 35 (最小 31、最大 52) |
| 1 階の滞在ターン (B10 以降) | 140〜153 |
| 総ターン 中央値 | 1772 |
| 総撃破 中央値 | 155 |
| 被弾の軽減率 | 57〜62% |
| 1 ダメージに潰れる率 (B4〜B9) | 70〜83% |
| 死因 1 位 | スタミナ切れ 56/200 (28%) |

B20 でレベル 35 は最大 HP 122 である。
同じ階の被弾は実ダメージ平均 1.97 なので、無抵抗で 62 発耐える計算になる。
「ぜんぜん死ぬ気がしない」という体感は、この比が正しく反映されたものである。

死因の 1 位が敵ではなくスタミナ切れなのは、1 階が長いことの帰結である。
スタミナは 7 ターンに 1 減るので初期値 150 は約 1050 ターンぶんであり、
B10 到達までの累計滞在ターンとほぼ一致する。
つまり今のゲームは、敵と戦って死ぬのではなく時間切れで死ぬ形になっている。

## 2. 診断

### 2.1 角越しの攻撃 (最優先)

移動は角の斜め抜けを禁じているのに、攻撃は距離だけで判定している。

- プレイヤー: `src/game.ts:329` で `monsterAt(nx, ny)` を先に見て、
  `canStep` を通さずに `playerAttack` を呼ぶ
- 敵: `src/game.ts:1220` の `dist === 1` で即攻撃する。`dist` はチェビシェフ距離である
- 群れ薙ぎ: `adjacentMonsters` (`src/game.ts:1033`) も同じくチェビシェフ距離だけで拾う

両者とも壁の角越しに殴れるので、通路の入口が防衛線にならない。
通路に 2 歩入らないと 1:1 にならないのは、この非対称ではなく「両者とも角を抜ける」ことが原因である。

### 2.2 敵の思考ルーチンが列を作る

`moveToward` (`src/game.ts:1299`) は候補を 3 つしか試さない。

```ts
const candidates = [[sx, sy], [sx, 0], [0, sy]];
```

3 つとも壁か他の敵で塞がると、その場に留まる。
迂回する候補が無いので、先頭の 1 体が詰まると後続は直線に並んで停止する。
群れ (`pack` が 2〜5) が数の利を出せないのはこのためである。

包囲が成立しないのも同じ理由で、全員が同じ最短方向へ向かうので 1 列になる。

### 2.3 レベルが上がりすぎる

獲得側と必要側の伸び方が釣り合っていない。

- 獲得: 1 階の敵数が `3 + depth + 0..2` で線形に増え、
  基礎経験値がグレードで 4 → 13 → 30 と跳ね、さらに `1 + 0.15 × depth` が掛かる。
  累計はおよそ深さの 3 乗で伸びる
- 必要: `xpToNext(level) = 6 + level(level+1)/2` は 2 次なので、累計は 3 乗で伸びる

3 乗どうしなので、レベルは階に対してほぼ線形になる。実測で 1.7 レベル/階である。
README の「どの階でも 3〜10 体で 1 レベル」という狙いは達成されているが、
1 階で 15〜24 体倒すので、狙いどおりに動いた結果としてレベルが 35 まで伸びる。

さらにレベルアップが全回復なので、経験値が実質「無限の回復薬」として働く。
下降圧 (スタミナ、毒、追う者) を足しても、レベルアップの頻度がそれを上回っている。

### 2.4 分裂の上限が効いていない (バグ)

`trySplit` (`src/game.ts:1155`) の上限判定が、グレード 1 の `slime` だけを数えている。

```ts
const slimes = state.monsters.filter((x) => x.kind === 'slime').length;
if (slimes >= SLIME_CAP) return;
```

`slime` の `maxDepth` は 10 なので、B11 以降に出る `slimeSplit` と `slimeMimic` では
この数が常に 0 になり、上限 4 が一度も働かない。

分裂した子は HP が半分になるだけで、`rewardKill` は `def.xp` から経験値を出す。
つまり殴って割るたびに経験値の総量が増える。
B11 以降で無限に経験値を稼げる状態であり、2.3 のレベル過剰を後押ししている。

README の「4 匹まで」という記述とも食い違っている。

### 2.5 防具が効きすぎる

軽減率は 60% 前後で上限の 75% には届いていないが、
出目そのものが小さいので、B4〜B9 では被弾の 7〜8 割が 1 ダメージに潰れている。
被弾しても減らないので、階に留まる判断が軽くなり、滞在ターンを押し上げている。

### 2.6 1 階が長い

40 × 30 の格子に部屋を最大 9 つ置き、視界は 7 マスである。
階段を探し、アイテムを拾い、湧いた敵を掃除すると 140 ターン前後かかる。

## 3. 改修の順番

数値の調整を先にやると、戦闘の形が変わったあとに測り直しになる。
戦い方を決める改修 (到達判定と AI) を先に置き、計測する側 (autoplay) を合わせてから数値を触る。

```
Step 0  分裂の上限バグを直す
Step 1  攻撃の到達判定を移動と揃え、角越しを遠距離能力として切り出す
Step 2  敵の思考ルーチンを作り直す (src/ai.ts に切り出す)
Step 3  autoplay に通路戦術を入れる
Step 4  1 階を短くする
Step 5  成長曲線と防御を測り直して合わせる
Step 6  game.ts を分割する
Step 7  新要素を足す
```

Step 0 から 3 までは数値を触らない。
Step 4 と 5 で初めてバランスを動かし、そこで一度まとめて計測する。

## Step 1: 攻撃の到達判定

### やること

`src/map.ts` に到達判定を足す。実体は `canStep` と同じ規則だが、意味が違うので名前を分ける。

```ts
/** (x, y) から (dx, dy) の隣へ攻撃が届くか。壁の角越しには届かない */
export function canReach(map: GameMap, x: number, y: number, dx: number, dy: number): boolean {
  return canStep(map, x, y, dx, dy);
}
```

呼び出し側を 3 か所直す。

1. `src/game.ts:329` プレイヤーの攻撃
   `monsterAt` が居ても `canReach` が false なら攻撃させず、ターンも消費しない
2. `src/game.ts:1220` 敵の攻撃
   `dist === 1` を「距離 1 かつ `canReach` が true」に変える
3. `src/game.ts:1033` `adjacentMonsters` (群れ薙ぎ)
   同じ制限をかける

棘鎧の反撃 (`thornsCounter`) は `monsterAttack` の中から呼ばれるので、
2 を直せば自動的に追随する。

### 角越しを能力として切り出す

`Passive` に `reach` を足し、これを持つ敵だけが角越しと距離 2 の攻撃を行えるようにする。

- `phasing` (壁抜け) は既に角の制限を受けない設計なので、そのまま例外として残す
- ドラゴンの `breath` は距離 2〜4 の技として既に分かれているので、変更しない
- 現時点で `reach` を持つ敵は作らない。Step 7 で槍型の敵を足すときに使う

こうすると「角越しに殴られたら、それは遠距離攻撃を持つ敵である」と読めるようになる。

### 影響と確認

通路の入口に立てば、部屋側の敵は正面の 1 体しか殴れなくなる。
1 歩で防衛線が成立するので、2 歩入り込む必要が消える。

連結性は変わらない。
`canStep` は `map.test.ts` の到達判定と同じ規則で、部屋は矩形・通路は直交線なので
「角越しでしか届かない位置に敵が固定される」状況は生まれない。
ただし念のため、次のテストを足す。

- 壁の角を挟んで斜めに並んだプレイヤーと敵が、互いに攻撃できないこと
- 同じ配置で `phasing` を持つ敵は攻撃できること
- 群れ薙ぎが角越しの敵を巻き込まないこと

受け入れ条件

- 既存の 191 件が通ること
- 上記 3 件のテストが通ること
- `npm run balance -- 200` で被弾回数が減ること (通路で戦えるようになるため)

## Step 2: 敵の思考ルーチン

### 設計

greedy な 3 候補をやめ、プレイヤーからの距離場を使う。
`src/sim/autoplay.ts` の `bfsStep` と同じ手法が既にあるので、それを本編側に一般化する。

`src/ai.ts` を新設して、次を置く。

```ts
/** プレイヤーからの歩数。canStep の規則で塞がれた先は -1 のまま */
export function distanceField(map: GameMap, from: {x: number; y: number}): Int32Array;

/** 敵 1 体の次の 1 歩を決める */
export function chooseStep(state, m, field): {dx: number; dy: number} | null;
```

40 × 30 = 1200 マスなので、距離場は毎ターン 1 回作り直しても負荷にならない。
敵の数だけ作るのではなく、`monstersAct` の先頭で 1 回作って全員で使い回す。

### 移動の決め方

1. 距離場が今より小さくなる隣接マスを集める (`canStep` の規則で通れるものだけ)
2. 空いているマスの中から、距離が最小のものを選ぶ
3. 同点なら、プレイヤーとの直線方向に近いものを選ぶ (見た目の自然さ)
4. すべて塞がっていたら、距離が今と同じマスへ動く (迂回)
5. それも無ければ待機する

4 が今は無いので列ができる。ここを足すだけで詰まりは大きく減る。

### 群れの包囲

`family` が `swarm` の敵には、目標マスの予約を足す。

1. プレイヤーの周囲 8 マスのうち、`canReach` でプレイヤーに届く空きマスを候補にする
2. `monstersAct` のループの中で、swarm の敵が 1 体ずつ「まだ誰も予約していない候補」を
   自分に最も近い順に取る
3. 予約したマスを目標にして距離場ではなく個別の経路で寄る
   (候補は 8 マスしかないので、距離場から逆算すれば足りる)

予約は 1 ターン限りの一時的なもので、`GameState` には持たせない。
セーブ互換を壊さないためである。

### ふらつき

`erratic` は今「半分の確率で完全にランダムな方向」になっている。
距離場に置き換えると噛み合わないので、
「候補のうち最短ではないものを確率で選ぶ」形にする。
挙動の意味 (狙いがそれる) は変わらない。

### 受け入れ条件

- 群れ 3 体をプレイヤーの正面の通路に置いたとき、10 ターン以内に
  1 体が接敵し、残りが後ろで停止すること (通路では列になるのが正しい)
- 同じ 3 体を開けた部屋に置いたとき、10 ターン以内に 2 体以上が
  プレイヤーの周囲 8 マスに入ること (部屋では囲むのが正しい)
- 壁を挟んだ袋小路に敵を置いたとき、停止せず迂回すること
- `npm run balance -- 200` で B1〜B10 の被弾回数が増えること

最後の 1 つは「敵が強くなった」ことの確認である。
増えなければ AI が働いていない。

## Step 3: autoplay に通路戦術

計測する側が新しい戦い方を使えないと、
「AI が損な戦い方をしている」前提で数値を過剰に緩めてしまう。
Step 5 の前に必ず入れる。

`src/sim/autoplay.ts` の `decide` に、隣接判定の前段として次を足す。

```ts
/** 歩ける隣接マスが 2 以下なら隘路とみなす */
function isChoke(state: GameState, x: number, y: number): boolean;
```

方針

1. 見えている敵が 2 体以上で、自分が隘路に居ないとき、
   最も近い隘路へ BFS で後退する (敵から遠ざかる向きを優先する)
2. 隘路に着いたら、敵が隣接するまで `wait` する
3. 隣接したら殴る (今の挙動)
4. 敵が 1 体だけなら、これまでどおり突っ込む
5. 後退の途中で HP が `potionAt` を割ったら、これまでどおり回復を優先する

`Policy` に次を足して、切り替えられるようにする。

```ts
/** この数以上の敵が見えたら隘路へ下がる。0 で無効 */
chokeAt: number;   // 既定 2
/** 隘路を探す範囲 (歩数) */
chokeRange: number; // 既定 8
```

`chokeAt: 0` にすれば従来の方針で回せるので、
「戦術の有無で到達階がどう変わるか」を比較できる。

受け入れ条件

- `chokeAt: 0` と `chokeAt: 2` の両方で 200 run が完走すること
- `chokeAt: 2` の方が B10 到達率が高いこと
  (高くならなければ、Step 1 と 2 のどちらかが意図どおりに効いていない)

## Step 4: 1 階を短くする

滞在 140〜150 ターンを 60〜80 に落とす。
手は 4 つあるが、推奨は上 2 つの併用である。

### 推奨する 2 つ

1. マップを縮める
   `MAP_W` 40 → 32、`MAP_H` 30 → 24、`MAX_ROOMS` 9 → 6。
   歩数がそのまま減る。視界 7 は据え置く (縮めると相対的に広くなる)

2. 敵の予算を減らして 1 体を濃くする
   `spawnMonsters` の `budget` を `3 + depth + 0..2` から `3 + depth/2 + 0..1` に。
   撃破数が半分近くに減るので、Step 5 の経験値調整とも噛み合う。
   減らしたぶん、基礎 HP と攻撃力を上げて 1 体あたりの重みを戻す

### 採らない 2 つ

3. 階段の方角を降りた直後に出す
   `stairsDirection` (`src/game.ts:1423`) が既にあるので実装は簡単だが、
   探索そのものを削るので、暗闇階に限る形でのみ検討する

4. アイテムを階段寄りに配置する
   寄り道が減るのは確かだが、「危ない方へ取りに行くか」という判断まで消える

### 受け入れ条件

- B10 以降の滞在ターンが 60〜80 に入ること
- 総ターン中央値が 900〜1100 に入ること
- 死因のスタミナ切れが 10% 以下に下がること
- マップ縮小後も `map.test.ts` の連結性テストが通ること
  (部屋が 6 つに減るので、生成の失敗率が上がっていないかも見る)

## Step 5: 成長曲線と防御

ここで初めて数値を触る。
Step 0 から 4 までで撃破数と被弾が動くので、先に計測し直してから決める。

### レベル

3 つの軸がある。単独ではなく組み合わせる。

| 軸 | 現状 | 案 |
|---|---|---|
| 必要経験値 | `6 + L(L+1)/2` | `6 + 1.5 × L(L+1)` (係数を 3 倍) |
| レベルあたりの最大 HP | `LEVEL_HP = 3` | 2 |
| レベルアップの回復 | 全回復 | 最大 HP の 1/2 |

この 3 つで B20 到達時のレベルが 35 → 22 前後、最大 HP が 122 → 62 前後になる見込みである。
B20 の出目平均 4.84 に対して 12 発ぶんなので、緊張が戻る水準になる。

ただしこれは Step 4 の撃破数削減を織り込む前の試算である。
README にあるとおり定数は敵の経験値表と対で決まるので、
Step 4 まで入れた状態で `npm run balance -- 200` を回し、実測から合わせ直す。

全回復をやめる点は README の設計意図
(「瀕死のまま踏み込んで全回復を取りにいくかどうかが判断になる」) に触れる。
半分回復でも「踏み込むか」の判断は残るが、意図を弱めることになるので、
必要経験値と `LEVEL_HP` の 2 つで足りるなら、全回復は残す選択もある。
測ってから決める。

### 防御

1 ダメージに潰れる率を 40% 以下に落とす。

- 「出目の 1/4 は必ず通る」を 1/3 にする
- または被ダメージの下限を 2 にする (出目が 2 以上のとき)

前者を推す。後者は序盤の弱い攻撃まで重くなる。

### 受け入れ条件

| 指標 | 現状 | 目標 |
|---|---|---|
| B20 到達時のレベル | 35 | 18〜22 |
| 1 ダメージ率 (B4〜B9) | 70〜83% | 40% 以下 |
| B10 到達率 | 83% | 60〜70% |
| B20 到達率 | 11% | 20〜25% |
| 死因のスタミナ切れ | 28% | 10% 以下 |

B20 到達率を上げつつ B10 到達率を下げるのは、
「序盤で気を抜くと死ぬが、上手く進めば深くまで行ける」形にするためである。
今は逆で、序盤は死なないが深層で時間切れになる。

## Step 7: 新要素

Step 1 で用意した `reach` と、Step 2 の包囲を前提にした敵を足す。
通路に下がる戦術が有効になったあとなので、それを崩す敵が意味を持つ。

| 案 | 内容 | 崩すもの |
|---|---|---|
| 槍持ち (`reach`) | 距離 2 から突く。角越しも届く | 通路で一列に並ぶ戦術 |
| 射手 | 直線上から撃つ。障害物で遮られる | 通路の奥に籠もる戦術 |
| 押し込み | 攻撃時にプレイヤーを 1 マス押し戻す | 隘路に立ち続ける戦術 |

系統としては `warrior` の変種か、6 つ目の系統を作るかを選ぶ。
文字と生き物を系統ごとに固定する現在の設計を守るなら、新しい系統にした方が読みやすい。

優先度は最後である。
Step 5 まででバランスが取れていないうちに足すと、原因の切り分けができなくなる。

## 4. 各ステップの計測コマンド

## 5. 一つだけ迷っている点

Step 4 の「敵の予算を半分にして 1 体を濃くする」は、
群れ (`swarm`) の設計と正面からぶつかる。
群れは数で押す系統なので、予算を削ると Step 2 で直した包囲が発動しにくくなる。

案としては、予算の削減を群れ以外に限る (群れの `pack` は維持し、
単体で出る系統の出現数を減らす) のが素直だと思う。
ここは実際に動かしてみないと判断しづらいので、Step 4 のときに一度相談したい。
